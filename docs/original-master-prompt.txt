# Master Prompt: Industrial Instrument Calibration Management & Compliance Platform

## 1. Role and Objective

Act as a senior full-stack engineer, Python backend architect, database designer, data engineer, and industrial quality-compliance specialist.

Build a complete, production-oriented web application called **CalibraTrack — Instrument Calibration Management & Compliance Platform**.

The platform must manage industrial instruments, calibration schedules, calibration certificates, maintenance work orders, production usage, downtime, overdue instruments, compliance alerts, corrective actions, and immutable audit trails.

This must be a working end-to-end application, not just a UI prototype. Implement the frontend, backend, relational database, synthetic data generator, compliance rules engine, validation suite, analytics dashboard, documentation, and deployment configuration.

All business rules must be deterministic, explainable, testable, and traceable to their source records.

## 2. Technology Stack

Use the following stack:

- Frontend: React, TypeScript, Vite, Tailwind CSS, shadcn/ui.
- Backend: Python 3.12+, FastAPI, Pydantic.
- Database: PostgreSQL.
- ORM and migrations: SQLAlchemy 2.x and Alembic.
- Data generation: Python, Faker, NumPy, pandas.
- Charts: Recharts.
- API documentation: FastAPI OpenAPI/Swagger.
- Authentication: Role-based access control with secure password hashing.
- Testing: pytest, HTTPX, and database integration tests.
- Deployment: Docker and Docker Compose.
- File handling: Secure certificate upload and download with metadata stored in PostgreSQL.
- Code quality: Type hints, structured logging, environment-based configuration, and meaningful error handling.

Use a modular architecture. Keep business logic in backend service modules rather than embedding it in API routes or frontend components.

## 4. Database Schema

Create migrations and relational models for the following entities.

Fields:

- `asset_name`.
- `serial_number`: unique.
- `instrument_type_id`: foreign key.
- `supplier_id`: optional foreign key.
- `location`.
- `department`.
- `criticality`: LOW, MEDIUM, HIGH, CRITICAL.
- `commissioned_at`.
- `retired_at`: nullable.
- `lifecycle_status`: ACTIVE, UNDER_MAINTENANCE, RETIRED.
- `created_at`, `updated_at`.

### InstrumentType

Fields:
- `instrument_type_id`: primary key.
- `type_name`.
- `measurement_unit`.
- `lower_tolerance`, `upper_tolerance`.
- `default_calibration_interval_days`.
- `description`.
- `created_at`, `updated_at`.

### CalibrationPlan

Fields:
- `plan_id`: primary key.
- `asset_id`: foreign key.
- `interval_days`.
- `effective_from`, `effective_to`.
- `acceptance_lower`, `acceptance_upper`.
- `certificate_required`.
- `use_restriction_policy`.
- `created_at`.

Support effective-dated plan history. Do not overwrite historical plans when the calibration interval or tolerance changes.

### CalibrationEvent

Fields:
- `calibration_id`: primary key, format `CAL-<asset-id>-2026-000001`.
- `asset_id`: foreign key.
- `plan_id`: foreign key.
- `supplier_id`: optional foreign key.
- `calibration_date`.
- `measured_value`.
- `reference_value`.
- `measurement_error`.
- `tolerance_limit`.
- `result`: PASS, FAIL, INDETERMINATE.
- `next_due_date`.
- `performed_by`.
- `impact_assessment_required`.
- `created_at`.

Calculate measurement error and pass/fail results from defined tolerances. Never randomly assign a result independently of the measurements.

### Certificate

Fields:
- `certificate_id`: primary key, format `CERT-<calibration-id>`.
- `calibration_id`: foreign key.
- `asset_id`: foreign key, retained for direct consistency validation.
- `certificate_number`: unique where present.
- `issue_date`.
- `valid_until`: nullable if validity is governed by another documented policy.
- `document_uri` or secure storage key.
- `verification_status`: PENDING, VERIFIED, REJECTED, EXPIRED.
- `verified_by`, `verified_at`.
- `created_at`.

Validate that the certificate asset matches the asset referenced by its calibration event.

### WorkOrder

Fields:
- `work_order_id`: primary key, format `WO-2026-000001`.
- `asset_id`: foreign key.
- `calibration_id`: optional foreign key.
- `work_order_type`: CALIBRATION, REPAIR, CORRECTIVE_ACTION, INSPECTION.
- `priority`: LOW, MEDIUM, HIGH, CRITICAL.
- `status`: OPEN, ASSIGNED, IN_PROGRESS, BLOCKED, COMPLETED, CANCELLED.
- `description`.
- `opened_at`, `scheduled_start`, `started_at`, `completed_at`.
- `downtime_minutes`.
- `assigned_to`.
- `created_at`, `updated_at`.

### ProductionUse

Fields:
- `use_id`: primary key, format `USE-<asset-id>-<timestamp>`.
- `asset_id`: foreign key.
- `production_batch_id`: optional.
- `used_at`.
- `duration_minutes`.
- `production_status`.
- `calibration_status_at_use`.
- `decision`: ALLOWED, BLOCKED, REQUIRES_REVIEW.
- `exception_id`: nullable foreign key to a documented exception.
- `decision_reason`.
- `created_at`.

### Supplier

Fields:
- `supplier_id`: primary key.

### Alert

### AuditRecord

Fields:
- `audit_id`: primary key.

- `entity_id`.

### Additional entities

Add these supporting entities because the workflow requires them:

- `ImpactAssessment`: failed calibration, affected production interval, potentially affected batches, risk evaluation, disposition, reviewer, assessment status.
- `CalibrationException`: requested extension, reason, approval, approver, effective interval, expiry, and permitted-use scope.

- `User`: identity, role, active status, and authentication information.
- `CalibrationPlanHistory` or effective-dated plan records if needed to preserve previous configuration.
- Explicit bridge tables for any many-to-many relationships.

Document every relationship's cardinality, nullability, uniqueness, effective dates, and lifecycle rules.

Use database constraints where appropriate, and validate joins with integration tests.

## 5. ID Conventions

Use deterministic, immutable identifiers:

- Assets: `AST-000001`.
- Calibration events: `CAL-<asset-id>-2026-000001`.
- Certificates: `CERT-<calibration-id>`.
- Work orders: `WO-2026-000001`.
- Production uses: `USE-<asset-id>-<timestamp>`.

Make ID generation configurable for datasets spanning multiple years. Use collision-safe counters and deterministic ordering. Do not derive IDs from mutable names.

Use ISO 8601 timestamps and a consistent timezone policy. Document whether calibration intervals use calendar days, UTC, or plant-local time.

## 6. Deterministic Synthetic Data Generator

Create a standalone, configurable generator in `generator/`.

Default seed: `20261022`.

Default scale:
- 2,000 instruments.
- 5,000 calibration events.
- 100,000 production-use events.
- Supporting suppliers, plans, certificates, work orders, alerts, assessments, exceptions, batches, and audit records.

Generate records over a configurable one-year period, with explicit start and end dates.

Support two modes:

- `starter`: small dataset for local development and rapid testing.
- `full`: the required baseline volume.

Example commands:

`python -m generator.generate --profile starter --seed 20261022`

`python -m generator.generate --profile full --seed 20261022`

`python -m generator.validate --input-dir data/generated`

Requirements:

1. Generate parent/master data before dependent records.
2. Generate valid baseline records before injecting anomalies.
3. Reference valid parent IDs for every dependent record.
4. Use deterministic pseudorandom generation with a fixed seed.
5. Generate realistic variation in instrument types, locations, criticality, calibration intervals, supplier usage, measured values, failures, downtime, and production usage.
6. Calculate derived values from source data.
7. Parameterize volumes and distributions in a configuration file.
8. Keep generation independent of the web server.
9. Use batch database insertion or efficient file generation for full-scale data.
10. Never use real customer, employee, confidential, or personal data.

### Baseline distribution

Define and document configurable distributions for:
- Instrument types and criticality.
- Calibration intervals.
- PASS, FAIL, and INDETERMINATE outcomes.
- Certificate completeness.
- Work-order types and completion durations.
- Production-use frequency.
- Approved exceptions and emergency extensions.
- Downtime and failure severity.

Avoid arbitrary distributions that contradict the business rules. Compute outcomes from generated measurements and lifecycle state.

## 7. Business Rules Engine

Implement a dedicated compliance service with unit tests.

### Calibration due dates

Calculate the due date from the applicable calibration plan and the relevant calibration completion date.

For example:

`next_due_date = calibration_date + interval_days`

Document the interval convention and handle plan changes using the effective plan applicable to the event.

Detect due-date inconsistencies and generate an alert with the expected and observed dates.

### Production-use decisions

For each production-use event, evaluate the historical calibration state at the event timestamp.

Consider:
- Latest applicable completed calibration.
- PASS, FAIL, or INDETERMINATE outcome.
- Calibration due date.
- Certificate requirements and verification status.
- Instrument lifecycle status.
- Applicable plan and its effective dates.
- Approved exceptions and their exact scope and expiry.
- Site policy and instrument criticality.

Return one of:
- `ALLOWED`
- `BLOCKED`
- `REQUIRES_REVIEW`

Store the decision, policy version, evaluated timestamp, and human-readable decision reason.

Do not treat an emergency extension as a blanket exemption. Require explicit authorization, defined scope, and an effective interval.

### Failed calibration

When a calibration fails:
1. Create or require a corrective-action work order.
2. Require an impact assessment.
3. Identify potentially affected production uses since the last known-good calibration, using documented historical rules.
4. Identify relevant production batches.
5. Record risk evaluation and disposition.
6. Raise a high-severity alert when required.
7. Preserve all state transitions in the audit trail.

A failed calibration must not be considered resolved simply because a work order exists. Track assessment and corrective-action completion independently.

### Certificates

Validate certificate-to-event and certificate-to-asset consistency, status, required metadata, and validity dates.

Detect:
- Missing required certificate.
- Certificate for another asset.
- Expired or rejected certificate.
- Certificate linked to an invalid calibration event.
- Duplicate certificate number.

### Alerts

Generate deterministic alerts for:
- Upcoming calibration.
- Overdue calibration.
- Prohibited production use.
- Missing or invalid certificates.
- Due-date mismatch.
- Failed calibration.
- Missing impact assessment.
- Unresolved corrective action.
- Expired exception.

Deduplicate alerts using documented business keys so repeated processing does not create duplicate open alerts.

### Audit trail

Record important state changes and compliance decisions as explicit events. Avoid silently overwriting historical information. Support audit history by asset, calibration, work order, certificate, user, and date range.

## 8. Required Anomaly Injection

After generating valid records, deliberately inject the following labelled scenarios:

1. **DUE_DATE_MISMATCH**
   - Create a calibration record whose stored due date differs from the plan-derived due date.
   - Preserve the expected due date in ground truth.

2. **EXPIRED_USE_WITHOUT_EXCEPTION**
   - Create a production-use event outside its permitted calibration window.
   - Ensure no applicable approved exception exists.
   - Expected decision: BLOCKED when the applicable policy prohibits use.

3. **CERTIFICATE_WRONG_ASSET**
   - Create a deliberately inconsistent certificate-to-asset association.
   - Ensure the anomaly is isolated and labelled.
   - The validator must detect it.

4. **MISSING_IMPACT_ASSESSMENT**
   - Create a failed calibration with no required impact assessment.
   - Expected outcome: a missing-assessment finding and corrective workflow requirement.

Store anomaly metadata in a separate `ground_truth.csv` and `ground_truth.json`.

Suggested fields:
- `case_id`.
- `entity_type`.
- `entity_id`.
- `issue_type`.
- `severity`.
- `expected_decision`.
- `expected_value`.
- `observed_value`.
- `injected_at`.
- `explanation`.

Keep ground truth entirely separate from application input features and operational tables. Do not use it to determine the compliance engine's answer.

Allow validation and evaluation code to read ground truth separately.

## 9. Validation and Reproducibility

Implement a comprehensive validation suite.

### Structural validation
- Primary-key uniqueness.
- Foreign-key integrity.
- Required-field completeness.
- Valid enums and units.
- Unique serial numbers and certificate numbers where applicable.
- Duplicate event detection.
- Valid bridge-table relationships.

### Temporal validation
- Calibration completion dates must be consistent with their lifecycle.
- Plan effective dates must be valid and non-overlapping for the same scope.
- Certificates must have valid issue and verification timestamps.
- Work-order start and completion dates must be chronologically consistent.
- Production-use timestamps must be checked against the applicable calibration window.
- Exceptions must be approved and effective before they can authorize use.

### Business validation
- Recalculate due dates independently.
- Reconcile measured values, error calculations, and outcomes.
- Reconcile certificates to calibration events.
- Check prohibited-use decisions.
- Identify failed calibrations without required impact assessments.
- Validate work-order downtime arithmetic.
- Check lifecycle transitions and alert resolution.
- Confirm every injected anomaly is detected by the corresponding validator.

### Reproducibility validation

Generate the dataset twice with the same seed and configuration.

Compare:
- Row counts per file/table.
- Canonicalized file checksums.
- Primary-key sets.
- Ground-truth labels.
- Validation results.

Use stable sorting, canonical serialization, fixed timestamp handling, and deterministic ID allocation. Exclude genuinely runtime-dependent fields from checksum inputs or derive them deterministically.

Generate `validation_summary.json` containing:
- Table row counts.
- Primary-key violations.
- Foreign-key violations.
- Business-rule violations.
- Expected anomaly counts.
- Detected anomaly counts.
- Ground-truth evaluation results.
- Reproducibility comparison results.

Keep expected injected anomalies separate from unexpected baseline integrity failures.
